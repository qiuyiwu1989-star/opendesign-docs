# 设计总监与 Studio 共用验收简报

2026-09-16。以下均为合成验收场景，不代表真实客户需求、教学效果或已经生成的作品。案例推荐必须另行检索并核对来源。

## A. 教师课程：如何判断一条信息是否可信

- 使用者：初中教师；受众：七年级学生。
- 目标：学生能区分主张与证据，并用来源、交叉验证和不确定性三个问题检查信息。
- 使用场合：40 分钟课堂；投影展示，附一页可打印活动单。
- 提供材料：一组明确标注为虚构的网络消息、来源对照材料、讨论题；不输入学生个人资料。
- 交付：8–10 页 HTML 演示稿与活动单内容；实际打印格式作为单独检查，不假定已支持 PDF 导出。
- 风格约束：投影可读、低信息密度；通过对照和逐步解释表达概念，避免装饰压过知识。
- 总监需给：2–3 种教学叙事/视觉方向、各自适用条件、一个推荐及理由；指出哪些材料尚不足。
- 第一轮修改：“第三页太抽象，换成一个可以分组讨论的例子。”
- 第二轮修改：“保留教师已经改好的定义，只缩短活动说明，并留出五分钟总结。”
- 验收：目标与活动一致；虚构消息不被当真；投影文字可读；指定修改之外的人工内容不变；教师能自行修改核心文字。

## B. 企业提案：一个服务流程改进试点

- 使用者：产品负责人；受众：业务主管与管理层。
- 目标：申请批准一个小范围试点，验证跨部门需求交接是否更清晰。
- 使用场合：15 分钟汇报；会后作为可阅读提案交付。
- 提供材料：合成访谈摘要、当前流程、两个方案、资源约束；未知数据明确标为待验证。
- 交付：8 页 HTML 演示或一份结构清楚的 HTML 提案，先由总监解释形式选择。
- 风格约束：简洁可信，问题—证据—方案—取舍—试点—决策请求；不得虚构节省金额或客户背书。
- 总监需给：2–3 个设计方向，说明信息组织和图表形式为何适合管理层；视觉选择需要可核对参考。
- 第一轮修改：“方案对比改成一张可直接作决策的表，把假设和已知事实分开。”
- 第二轮修改：“保留手工修改的预算说明，只调整试点时间线和风险页。”
- 验收：决策诉求明确；事实有来源或标为假设；局部修改不覆盖预算；转入 Docs 后可改字、保存、实际导出并重导入。

## 共用评审记录

每次走查记录：输入版本、案例/设计包版本、推荐方向、采用或拒绝理由、事实错误、版式问题、人工修改范围、最终交付证据。目标用户评审与 AI 自检分开，不用一个总分掩盖来源或数据保全失败。

上述场景先用于产品定义和确定性验收。真实模型评估另行记录模型配置、用量及运行结果；不能用预制样例冒充真实生成。
