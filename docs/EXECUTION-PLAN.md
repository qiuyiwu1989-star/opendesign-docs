# OpenDesign 执行计划

更新：2026-09-16。用户已同意按 PRODUCT-STRATEGY.md 的顺序推进。此处记录执行状态，不以计划代替验收；开发与产品定义可继续推进，公开部署仍需对应发布授权。

## 执行原则

主线一次推进一个完整用户结果。我负责代码核对、实现、验证和文档维护；产品负责人在真实样例走查时判断推荐是否合适。未指定其他人员，不虚构排班。按验收门推进，不承诺未经容量核实的日期。

## 第二期：Library 与设计总监

目标：用户能从需求出发，选择一个有来源、有理由的设计方向。

- [x] 建立课程与企业提案两份合成需求简报，见 SCENARIO-BRIEFS.md。
- [ ] 按课程、企业提案、分析报告三个专题建立候选清单；先审查每个案例的来源、适用场景、设计解释和资产可用范围。
- [ ] 定义首页的精选、专题、案例详情与“带入创作”路径；先做可走查原型。
- [ ] 对两份简报各输出 2–3 个方向及推荐理由；记录适用条件、反例、取舍和未决问题。
- [ ] 用户走查后，确定设计总监输入/输出契约和首个精选专题，再开发入口。

完成门：用户能说明选择哪个方向以及为什么；推荐具有可核对案例依据；AI 评审和人工判断分开。未完成来源核验的候选不得当成精选发布。

## 第三期：Studio 最小创作闭环

目标：完成一份企业提案，经过两轮对话修改，交给 Docs 精修。

- [ ] 核对现有 Design Director、模型适配、版本与生成任务能力，区分历史完成记录与当前运行证据。
- [ ] 基于第二期契约写最小功能 spec：需求 → 大纲/样张 → 完整 HTML → 局部修改 → Docs。
- [ ] 为目标页/段落绑定修改范围及基线版本；用户接受前保留原稿。
- [ ] 验证取消、失败、恢复和重新生成，确保不覆盖人工修改。
- [ ] 用同一合成简报完成两轮真实修改及文件交付。

完成门：作品可读、可编辑、来源准确；只改指定范围；用户可恢复上一版本；数据与版式通过实际交付检查。

## 第四期：运行底座与产品扩展

- [ ] 写 DSH 适配决策记录：比较现有流程与 DSH 的同任务完成率、局部修改、恢复、用量和维护成本。
- [ ] 明确试验环境与模型预算后，运行 6 个固定任务；在采用决定之前不迁移整个 Studio。
- [ ] 教育与企业各选择一个真实用例，限定传入数据与用途；先单向交接，再评估回写。
- [ ] 有重复使用证据后定义团队权限、长期存储与高级额度；再考虑收费。

## 下一次执行起点

以深脑新回执为准，先取得开关生效机制与九图合成样本，完成兼容检查并准备 Docs 静态接收端发布候选。独立 MCP 服务不是深脑按钮的上线依赖。若需检查或改动深脑代码，才继续锁定其实际发布工作树，避免重复实现已完成按钮。

## 汇报方式

每完成一个验收门，更新本文件、TASKS.md 和对应证据。失败时记录具体阻碍及下一个可执行动作。需要公开发布、真实数据或模型预算时，先准备好可审查方案再处理该项授权。此计划未创建自动定时任务或后台持续运行任务。
