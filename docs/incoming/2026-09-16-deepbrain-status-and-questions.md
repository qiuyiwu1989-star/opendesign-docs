## 2. 我们**没有**用你们的浏览器 SDK

我们按 Spec036 的 v1 契约自己实现了一份客户端，行为与 SDK 一致。原因是站点策略：我方页面的脚本只允许来自自己的域名，为一个按钮增加一条外部脚本来源，代价是所有页面多一个可被注入的入口。这不是对 SDK 的质疑。

**副作用请你们知悉**：SDK 以后改了，我方不会自动跟上。**协议若有 v2，请在文档里标明版本与变更**，我方按版本跟进。

我方实际发出的消息（供你们对照）：

```jsonc
// 收到 READY（校验：window 是我们开的那个、origin 精确匹配、v===1、nonce 长度 16–128）之后
{ "type": "opendesign:handoff", "v": 1, "nonce": "<原样回传>",
  "document": { "name": "深脑-<标题>-<8位id>.html", "html": "<!doctype html>…", "bytes": 123456 } }
```

`document.bytes` 是我方多带的一个字段（UTF-8 字节数，我们自己先挡 5 MiB 用的）。**如果你们的校验对未知字段严格，请告诉我，我去掉。**

我方对 RESULT 的处理：`ok:true` 才算成功；`ok:false` 只认 `rejected / too_large / invalid / timeout / storage` 这五种理由，其余忽略。**断连、超时、窗口被关一律不自动重发**（按你们文档：对方可能已经存下了）。

## 3. 我们验过什么、没验过什么

验过（12 条协议测试）：正常握手、用户取消、对方保存失败、来源窗口不对、origin 不对、协议版本不对、nonce 太短、重复 READY、结果 nonce 对不上、等 READY 超时、报告生成超时、弹窗被拦、窗口被关、超过 5 MiB 在本地就挡住不发。

**没验过：真实浏览器里两个窗口的握手。** 我方这台机器的自动化浏览器把 `window.open` 开成了同一个标签页，opener 链路断掉，你们的 Docs 正确地报了「无法连接来源页面」。所以**真机联调这一步双方都还没做过**，这是公网验收要过的第一关。

## 4. 我方报告的形态（你们编辑侧可预期）

- 自包含 HTML：内联 `<style>`、**零脚本、零外链**（字体只用系统字体栈）。
- 图表是**静态内联 SVG**，没有 `<script>`、没有 `foreignObject`、没有 canvas；原来的 mermaid 流程图现在也由我们自己画成静态 SVG。
- 正文里的判断带上标锚点，链接到文末证据区（`<a href="#ev-N">`），**站内锚点，不外链**。
- 结构：`<main><article>` + `header.report-head` + `section.report-body`（h2/h3/p/table/figure）+ `section.evidence`。
- 亮暗两套主题：用 `prefers-color-scheme` 覆盖 CSS 变量，不改 DOM。
- 体积：一份典型报告（9 张图）约 40–120 KB，远低于 5 MiB。
